# 自备卡密库存与自动交付设计

状态：待用户审阅

## 背景

商城使用 GPTibo 的 React 前端、Go API 和 PostgreSQL。当前订单交付可由管理员逐单录入一份兑换码；数据库尚无通用卡密库存池。本项目部署的支付和邮件发送功能仍需单独配置。

用户希望销售 AI 会员或充值类数字商品，选择付款后交付兑换码/卡密，并优先自行采购、分批存入库存。首期不接可产生供应商采购支出的 API，以便把库存暴露风险限制在当时存放的卡密数量和价值内。

## 目标

- 管理员能按商品套餐批量导入自有卡密，并查看每个套餐的可用、预留和已发放数量。
- 每个有效卡密最多分配给一个订单；库存不足时停止接受新的该套餐订单。
- 只有经现有支付流程确认已付款的订单才能领取卡密。
- 重复支付回调、任务重试和重复页面请求都不能分配第二张卡密。
- 卡密不出现在日志、分析数据、库存列表或管理端导出中。
- 供货方式可以在未来扩展到供应商适配器，但首期不保存任何供应商钱包或采购 API 凭据。

## 不在首期范围

- 接入新的收款渠道或启用现有未配置的真实支付渠道。
- 供应商 API 自动采购、上游余额管理、库存同步。
- 新增或确定 ChatGPT、Claude、Codex 等具体商品的售价、映射和销售资格。
- 通过邮件正文发送卡密。首期在订单详情中交付；后续可增加不含卡密的邮件提醒。
- 自动验证卡密是否已被上游兑换，或自动处理已发码订单的退款。

## 方案比较

1. **逐单手工填码**：改动少，当前部分商品已有交付流程；人工工作量随订单量增长。
2. **自备卡密库存**：导入少量现有码，付款后自动分配；无需把有余额的供应商凭据放到服务器。推荐作为首期。
3. **供应商 API 自动采购**：可自动补货，但要保存具有消费权限的凭据，并依赖具体供应商协议；留作未来独立阶段。

## 设计

### 商品和库存

- 库存以现有商品套餐 ID 为归属；本次不改变套餐目录或价格。
- 管理后台提供卡密库存区：选择套餐，粘贴或上传文本文件，每行一个卡密。单次导入最多 50 条。
- 导入先完整验证，再原子写入；空行可忽略，格式错误、批内重复或已存在的重复卡密会让整批导入失败，并且错误信息不回显卡密内容。
- 后台只显示批次、导入数量和库存状态，不提供明文回看、下载或批量导出。错误码需要补充或撤销时，通过新批次处理。
- 卡密状态为 `available`、`reserved`、`issued`；状态变更保留时间、订单和管理员审计记录，不记录卡密明文。

### 存储与保密

- 使用 AES-256-GCM 加密保存卡密；使用带密钥的 HMAC 指纹完成重复检查。加密密钥和指纹密钥来自独立的运行时秘密文件，不写入 Git、数据库或普通配置值。
- 数据库备份只包含密文。完整服务器或运行进程被攻破时，攻击者仍可能读到当时可用的卡密；加密不能替代分批少量补货和管理员账号保护。
- 对包含交付资料的响应设置 `Cache-Control: no-store`，且不得记录响应体、导入请求体或解密后的卡密。
- 真实导入前必须启用管理后台身份验证和双因素验证；当前线上管理员邮件登录尚未配置。

### 下单、预留与发放

1. 创建订单时，后端在数据库事务中锁定该套餐的一张 `available` 卡密并标记为 `reserved`，关联该订单及现有支付有效期。没有可用卡密时拒绝创建新订单。
2. 收到并验证支付成功后，在同一事务中把该订单预留卡密改为 `issued`，让现有订单详情接口只向该订单的已验证访问者返回一次分配结果。重复支付通知只确认原分配，不再消耗库存。
3. 订单取消或支付明确过期后释放预留卡密。清理任务只处理已确认过期的订单；不得仅凭本地时间把仍有支付可能的订单卡密重新分配。
4. 如果支付成功通知到达时预留已失效，优先尝试原子分配另一张可用码；若库存已空，订单标为待人工处理并通知管理员，不伪造发货成功，也不自动重复扣款或采购。
5. 商品库存为零时从商城隐藏或禁用下单。付款状态和卡密发放状态独立记录，以便售后核对。

### 客户交付

- 客户在原订单详情页查看、复制所属订单的卡密和领取说明；页面重复打开仍显示同一张码，不会再次扣库存。
- 订单访问沿用现有订单授权，不向公共商品目录或普通订单列表返回卡密。
- 首期不把卡密放进邮件正文；邮件服务启用后可以只发送“订单已有交付资料”的提醒。
- 码一旦向已付款客户显示，就视为已交付，不能自动回收给其他订单。退款及争议按人工售后流程处理。

## 数据和接口边界

- 新增库存表和必要的迁移、过期预留清理逻辑。
- 增加仅管理员可用的库存摘要与批量导入接口。
- 扩展订单创建、付款确认和订单详情读取，使用数据库事务、行锁、幂等键及现有订单授权。
- 加密配置缺失或格式不正确时，库存导入和卡密交付均关闭并明确报错；不降级为明文保存。

## 验收标准

- 导入能显示数量结果；重复卡密和单批超过上限时不会产生部分写入。
- 两个同时付款的订单不能拿到同一张卡密；一个支付回调重放不能多发一张。
- 未付款、退款中、已退款或被暂停的订单不能领取卡密。
- 订单过期后可释放预留；已确认付款的迟到回调不会把已发卡密重复发给其他订单。
- 库存为零时不能创建该套餐的新订单。
- 客户订单页可以领取自己的卡密，其他客户或未授权请求拿不到卡密；相关响应不被缓存。
- 日志、审计记录和管理端库存列表不含卡密明文。
- 本地执行项目规定的前端构建和 Go 静态验证；不在服务器构建。

## 运营前置条件

- 配置并验证管理员登录、邮箱验证和 TOTP；只有授权管理员能导入库存。
- 单独选择并配置支付渠道。当前线上支付功能关闭，因此仅完成库存功能并不能开始真实销售。
- 确认每个商品码的来源、有效期、兑换区域、退款条件及对应套餐说明后，才导入真实库存。
- 部署数据库迁移前，在香港服务器按项目规则检查服务状态、数据位置并创建可验证的备份；构建产物在本地 Windows 构建后再部署。
